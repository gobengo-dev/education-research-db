# Provenance Model

---

# Design Goal

The provenance system exists to ensure that every harvested or derived entity can be traced back to:

- source system
- harvest run
- ingestion method
- processing pipeline
- discovery context
- retrieval timestamp

The goal is to support:

- reproducibility
- auditability
- rebuildability
- incremental harvesting
- future multi-source integration

---

# Core Principles

## Raw records are immutable

Raw harvested records should never be overwritten destructively.

## Derived layers are rebuildable

Flattened or canonicalised layers should be reproducible from raw layers.

## Provenance survives transformation

Derived records should retain links back to originating harvests.

---

# Core Tables

## harvest_runs

Represents a harvesting operation.

Examples:

- OpenAlex expansion harvest
- Crossref DOI enrichment run
- ORCID profile harvest

Key fields:

- harvest_run_id
- source_system
- script_name
- started_at
- completed_at
- configuration_json

---

## harvest_sources

Represents harvesting targets.

Examples:

- OpenAlex topic
- OpenAlex source
- Crossref DOI scope

---

## raw_source_records

Stores raw harvested source records.

Examples:

- raw OpenAlex work JSON
- raw Crossref DOI JSON
- raw ORCID profile JSON

Important:

This table preserves source-system-level records before flattening.

---

## source_work_claims

Tracks claims that a source record corresponds to a work.

Supports:

- many-to-many harvesting
- duplicate discovery
- journal harvesting provenance
- topic harvesting provenance

---

## work_identifier_claims

Tracks identifiers associated with works.

Examples:

- DOI
- OpenAlex work ID
- ISBN

Supports:

- conflicting identifiers
- multiple-source identifier validation
- future reconciliation

---

## source_record_discovery_events

Tracks how records were discovered.

Examples:

- discovered through topic harvesting
- discovered through journal harvesting
- discovered during delta DOI enrichment

This is critical for future auditing.

---

## processing_runs

Represents derived-table generation.

Examples:

- publication output layer rebuild
- canonical source generation
- institutional normalisation

---

## processing_outputs

Tracks outputs generated by processing runs.

Supports rebuild auditing.

# Future Goals

## Full lineage tracking

Eventually every derived record should support full lineage traversal.

## Version-aware rebuilds

Derived layers should become versioned and reproducible.

## Processing DAGs

Future processing should resemble explicit dependency graphs.

## Harvest manifests

Future harvest runs should generate machine-readable manifests.

---

# Important Constraint

The provenance layer is append-oriented.

Future harvesting should:

- append provenance
- preserve historical state
- avoid destructive overwrites
- maintain source traceability
